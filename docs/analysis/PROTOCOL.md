# 백테스트 프로토콜

`/backtest` · `/backtest-refresh` 스킬과 모든 독립 백테스트 세션이 따르는 공통 규약.
이 파일을 읽지 않고 백테스트를 시작하지 않는다.

## 1. 데이터

- **로컬 캐시만 사용한다.** 재다운로드하지 않는다.
  - KR: `cache/prices_kr.parquet` · US: `cache/prices_us_test.parquet` · 지수: `cache/prices_bench.parquet`
- 결과 문서에 **데이터 기준일**(각 parquet의 마지막 봉 날짜)을 반드시 기록한다.
- 캐시 마지막 봉이 실행일보다 **6개월 이상** 오래됐으면 결과 문서와 종료 출력에
  "캐시 갱신 권고"를 명시한다 (갱신 방법: US `PYTHONPATH=. python docs/analysis/scripts/us_download.py`,
  KR은 `python -m pipeline.run --market kr`).
- 알려진 데이터 이상: 종가 0 구간 종목(CBIO·DEC) → `btlib` 로더가 자동 제외.

## 2. 고정 파라미터 (가설이 명시적으로 바꾸지 않는 한)

| 항목 | 값 | 근거 |
|---|---|---|
| 레짐 필터(시장 강세) | 벤치마크 종가 > SMA200 | `config.REGIME_SMA`와 동일 |
| 거래비용 | US 0.10% · KR 0.28% (왕복, 수익률에서 차감) | 2026-07-29 검증과 동일 |
| 최소 이력 | 이벤트 방식 900봉 · walk-forward 500봉 | 〃 |
| walk-forward 간격 | STEP=20 (월 1회) | 〃 |
| 유동성 필터(US) | 진입 시점 직전 20봉 평균 거래대금 ≥ $2M (**PIT — look-ahead 금지**) | 〃 §5-② |
| 최대 추적 | 504봉 | 〃 |
| 난수 시드 | 고정하고 문서에 기록 | 재현성 |
| 벤치마크 | ^GSPC(US) · ^KS11(KR) | `config.BENCHMARKS` |

## 3. 사전 판정 기준 (pre-registration)

**결과를 보기 전에** 가설 문서에 통과/기각 조건을 고정한다. 최소 요건:

- 초과수익(벤치마크 차감)이 **평균과 중위 둘 다** 양수일 것
- **KR·US 양 시장에서 일관**될 것 (한 시장 통과는 "부분 지지"로만 기록)
- 비용 반영 후 기준일 것
- 한 칸만 좋은 결과는 우연으로 간주 (다중비교 경계)

## 4. 검토 체크리스트

### (a) 가설 게이트 — 테스트 시작 전, 독립 sub-agent(Opus), 최대 3회

- [ ] `hypotheses/registry.md` 전체와 대조해 중복 아님 (구조 동일 = 중복)
- [ ] `hypotheses/jail.md` 기준으로 이 시스템 데이터로 구현 가능
- [ ] 조건 부합: 심플 / 추세추종 계열(확장 범위 포함: 듀얼 모멘텀·리밸런싱·레짐 분리 허용) / 시장 강세일 때만 매수
- [ ] 사전 판정 기준이 결과 산출 전에 고정돼 있음
- [ ] 매수·매도 규칙이 일봉 종가 기준으로 모호함 없이 기술됨

### (b) 코드 + 결과 검토 — 테스트 후, 독립 sub-agent(Opus), 1회

- [ ] look-ahead 없음 (미래 봉·최종일 기준 필터·`tail()` 사용 여부 grep)
- [ ] 유동성 필터가 진입 시점 기준(PIT)인가 (US)
- [ ] 벡터화 로직은 소표본 루프 구현과 대조했는가 (2026-07-29 §5-① 재발 방지)
- [ ] 비용 반영, 겹치는 창이면 독립 표본수 명시, 생존편향 한계 명시
- [ ] `btlib` 공용 모듈을 사용했는가 (새로 짠 부분은 왜 필요했는지 설명)
- [ ] 결과 판정이 사전 기준·실제 숫자와 일치하는가

### (c) 문서 검토 — 아카이브 작성 후, 독립 sub-agent(Opus), 1회

- [ ] 가설·설계·사전 기준·데이터 기준일·시드·결과·판정·한계가 모두 있는가
- [ ] 숫자가 스크립트 출력과 일치하는가
- [ ] 재현 방법(실행 명령)이 있는가

## 5. 아카이브 규칙

- 결과 문서: `docs/analysis/backtests/YYYY-MM-DD-<slug>.md`
  (필수 섹션: 가설 / 사전 판정 기준 / 설계 / 데이터 / 결과 / 판정 / 한계 / 재현 방법)
- 테스트 스크립트: `docs/analysis/backtests/scripts/<slug>.py` (btlib 사용)
- registry 상태 갱신(`채택`/`기각`) + `SUMMARY.md` 맨 위에 초보자 요약 추가
- **테스트당 git 커밋 1개. push는 하지 않는다** (사용자 판단)

## 6. 운영 규칙

- **수정 허용 경로**: `docs/analysis/**` 만. `pipeline/` `site/` `tests/` `scripts/`
  `.github/`는 읽기 전용 (import는 허용, 수정 금지)
- **동시 실행 금지**: registry·SUMMARY는 공유 파일이므로 백테스트는 한 번에 한 세션만
- **모델 배분**: 본 분석·문서 작성은 Opus 세션 권장. **§4의 검토 3종((a)(b)(c))은
  모두 독립 sub-agent + Opus 고정.**
  - **독립성이 필수 조건이고, 모델 등급은 그 위에서 검출력을 정한다.** 코드를 작성한
    세션이 자기 코드를 직접 검토하면 같은 가정을 그대로 들고 보게 되므로, Opus로 해도
    게이트가 무력해진다. 그래서 반드시 sub-agent로 띄우고, 그 위에 등급을 올린다.
    (이 제약은 §4의 검토 3종에 적용된다. `/backtest-refresh`의 수혈 판정은 본 세션이
    직접 수행하며 여기에 해당하지 않는다.)
  - 등급을 올리는 이유는 **위험의 비대칭**이다. 작성 실패는 재실행으로 되돌릴 수 있지만,
    검토 실패는 조용히 통과해 **틀린 결론이 아카이브에 영구 기록**되고 registry가 그것을
    근거로 이후 가설의 중복을 판정하므로 오류가 뒤 테스트로 전파된다.
  - 특히 (b)는 신규 계산 로직의 버그를 찾는 판단 작업이다. 이 프로젝트에서 확인된 버그는
    전부 신규 구현 코드에서 나왔다(2026-07-29 §5의 벡터화 연속 카운트 오류·거래대금
    필터 look-ahead).
- 테스트 종료 시 SUMMARY.md의 해당 항목을 **화면에 그대로 출력**한다
